# 하나의 테마로 iOS·Android를 편집하는 흐름 검토

구현 완료 안내: 후속 승인으로 0.5.0에 구현했다. 현재 동작과 검증은 [REVIEW-0.5.0.md](REVIEW-0.5.0.md), HANDOFF.md, VERIFICATION.md를 따른다. 아래는 구현 전 검토 기록이다.

검토일: 2026-10-26. 대상: 앱 0.4.0 / compilerVersion 0.4.1. 이번 작업은 검토이며 기능 구현은 포함하지 않는다.

## 결론

기본 제작 흐름을 `화면 선택 → 공통 이미지 한 번 등록 → 두 플랫폼 확인 → 필요한 예외만 조정`으로 바꾸는 것이 적절하다. 현재도 공통 원본에서 두 플랫폼을 생성할 수 있지만, 화면의 기본 편집 동선은 플랫폼별 카탈로그를 먼저 보여 준다. 생성 엔진을 새로 만들기보다 기존 공통 원본을 중심으로 편집 UI와 예외 관리 흐름을 정리하는 것이 우선이다.

## 현재 동작과 불편의 원인

| 확인 사항 | 구현 근거 | 사용자에게 미치는 영향 |
|---|---|---|
| 공통 원본 한 번 등록으로 양 플랫폼 생성 가능 | `src/core.mjs`의 SLOTS/assets, `src/server.mjs`의 POST assets, `compile()` | 배경·말풍선·탭·프로필·비밀번호 이미지를 각각 두 번 등록할 필요는 없다. |
| 공통 입력은 접힌 영역에 있음 | `public/index.html`의 `details#screen-sources`에 open 없음 | 화면별 제작 중 공통 등록 기능을 찾기 어렵다. |
| 카탈로그의 최초 탭은 iOS | `public/catalog-editor.js`의 초기 `tab='ios'` | 공통 테마 제작보다 플랫폼별 항목 편집으로 시작하게 된다. 이후에는 선택한 탭을 유지한다. |
| 전체 이미지의 논리 그룹도 플랫폼별 | `src/catalog.mjs`의 `logicalResource()`, 편집기의 `singleResource` 요청 | `모든 배율·화면에 적용`도 선택한 플랫폼 그룹에만 적용된다. 양쪽 플랫폼을 뜻하지 않는다. |
| 출력별 재정의가 공통 원본보다 우선 | `src/resources.mjs`, `src/provenance.mjs` | 공통 원본을 교체해도 이미 따로 등록한 출력은 바뀌지 않는다. |
| 템플릿 ZIP 일괄 등록은 출력별 재정의를 만듦 | `src/editor-service.mjs`의 `resourceTemplate()` / `applyResources()` | 전체 템플릿을 재등록하면 146개 출력이 각각 고정될 수 있다. 이후 공통 원본 수정의 효과가 가려진다. |
| 크롭·이미지 사용 여부는 플랫폼별 논리 그룹, 가이드는 출력별로 저장 | `resourceOptions`, `resourceGeometry`, iOS overrides | 원본 공유와 출력 모양의 독립 조정을 함께 표현해야 한다. |

공통 입력은 47개이며, 현재 카탈로그의 원본 후보 체인을 대조하면 35개는 양 플랫폼 출력에 연결되고 12개는 한 플랫폼 전용이다. 후보 연결에는 대체 원본도 포함되므로 모든 연결이 동시에 활성인 것은 아니다. iOS 선택 말풍선·키패드 눌림, Android 추가 프로필·시작화면·친구 추가 누름 이미지는 전용 기능으로 명시해야 한다.

## 권장 편집 흐름

1. 화면별 첫 영역을 펼쳐진 `공통 디자인`으로 제공한다. `채팅방 배경`, `보낸 말풍선`, `친구 탭 · 기본/선택`, `비밀번호 1 · 입력 전/후`처럼 디자인의 역할과 상태로 표시한다. 비밀번호 이미지 8개와 첫/연속/선택 상태는 유지한다.
2. 각 항목은 원본 썸네일과 `iOS·Android 공통`, `iOS 전용`, `Android 전용`을 표시한다. 파일명과 배율은 세부 영역에서 확인한다. 원본을 등록하거나 교체하면 assets의 같은 슬롯을 계속 참조하게 한다.
3. 현재 출력이 공통 원본을 사용하는지 플랫폼·상태·배율별로 표시한다. 단순 출력 총수뿐 아니라 `Android: 개별 이미지 유지`, `iOS: 이미지 사용 안 함`처럼 적용되지 않는 이유와 해당 편집기로 이동하는 경로를 제공한다.
4. 기존 예외는 유지한다. 사용자가 대상 출력을 선택해 `공통 원본으로 연결`하면 해당 이미지 재정의를 해제한다. 가이드·크롭·이미지 비활성화는 별도 설정이므로 자동으로 초기화하지 않고 남아 있는 차이를 표시한다. 변경은 한 번의 실행취소로 복원할 수 있어야 한다.
5. 현재 플랫폼별 카탈로그는 `플랫폼별 세부 조정`으로 제공한다. 같은 catalog-editor 인스턴스를 계속 사용하고, 모든 상태·배율·9-patch 접근 경로를 유지한다. 공통 원본 교체 시 개별 편집기와 양쪽 미리보기의 적용 상태도 함께 갱신한다.

예를 들어 `보낸 말풍선 · 첫 번째`에 PNG를 한 번 등록하면 같은 원본에서 iOS @2x/@3x와 Android 9-patch를 생성한다. Android만 다른 그림이 필요하면 세부 조정에서 재정의한다. 이후 공통 이미지를 교체할 때 Android의 예외 유지 사실을 바로 표시한다. 같은 원본을 써도 플랫폼의 크기·크롭·늘림 규칙에 따라 최종 모양은 달라질 수 있다.

## 기존 프로젝트 전환

- 기존 프로젝트는 현재 결과를 유지한 상태로 연다. 두 플랫폼에 서로 다른 이미지가 있으면 어느 쪽을 공통 원본으로 쓸지 자동으로 추정하지 않는다.
- 세부 이미지에서 `이 이미지를 공통 원본으로 사용`하는 경로를 제공하고, 연결될 출력과 유지할 예외를 먼저 보여 준다. Android 원본 .9.png는 가이드 테두리를 분리한 내부 그림을 공유해야 하며, 다중 가이드는 Android에 보존해야 한다. 이 변환은 별도 구현·검증 범위다.
- 양 플랫폼의 출력별 재정의에 같은 파일을 복사하는 방식은 피한다. 공통 원본의 후속 교체가 계속 전달되도록 assets를 공유하고, resourceOverrides는 실제 예외에만 쓴다.
- 기존 템플릿 ZIP은 출력별 세부 편집 용도로 명시한다. 추후 공통 원본용 일괄 등록을 제공한다면 역할·상태와 슬롯의 명시적 매핑을 사용한다. 플랫폼 파일명의 유사성만으로 연결하지 않는다.

## 구현 범위와 순서

우선 공통 이미지의 기본 노출, 지원 플랫폼 표시, 적용/예외 목록, 선택한 출력의 공통 연결을 구현하는 것이 효과적이다. 기존 assets/resourceOverrides 구조를 활용할 수 있으며, 원본 공유만을 위해 새 프로젝트 포맷을 도입할 필요는 없다. 출력 생성 규칙을 유지하는 UI 변경에는 compilerVersion 변경이 필요 없다.

화면별 색상 공통 편집과 공통 크롭 정책은 다음 범위로 분리하는 편이 안전하다. 현재 10색 팔레트는 여러 화면에 영향을 주므로 잠금화면 등의 색상을 통일하려고 전역 팔레트를 임의로 바꾸면 안 된다. 의미가 대응하는 iOS/Android 속성을 명시적으로 묶어 해당 overrides만 수정하고, 값이 다르면 혼합 상태를 표시하는 방식부터 검토한다. Android ARGB와 iOS 색상/투명도의 차이도 보존해야 한다. 새 공통 정책 필드나 변환 규칙을 도입하면 검증·캐시·복제·백업·실제 생성과 compilerVersion을 함께 갱신한다.

## 미리보기에서 설정으로 이동하는 탐색 개선 (추가 검토)

설정의 위치를 외우지 않고 미리보기에서 수정할 부분을 선택하는 흐름을 우선 제공하는 것이 적절하다. 현재 `public/preview-renderer.js`는 Canvas에 화면을 그리며, 요소별 DOM이나 클릭 영역은 없다. `public/app.js`는 화면 전환만 연결한다. `catalog-editor`도 현재 화면/탭/그룹 이동은 지원하지만 특정 속성·출력·배율을 지정해 여는 외부 진입점은 없다. 따라서 그리기 영역의 선택 정보와 편집 대상 이동 기능을 추가해야 한다.

### 권장 사용자 동작

| 미리보기에서 선택한 부분 | 오른쪽 설정의 목적지 |
|---|---|
| 채팅방의 빈 배경 | 채팅방 배경 이미지와 해당 화면 배경색 |
| 보낸/받은 말풍선 | 해당 방향·첫/연속·선택 상태의 이미지, 글자색, 늘림·여백 |
| 친구/채팅 목록의 프로필 | 현재 검토 중인 기본/전체·프로필 번호의 원본 이미지 |
| 탭 아이콘 | 해당 탭과 기본/선택 상태의 공통 원본 및 플랫폼 예외 |
| 비밀번호 표시 | 선택한 1~4번과 입력 전/후 상태의 원본 이미지 |
| 키패드·입력창·배너·버튼 | 선택한 부분의 이미지·색상과 현재 상태에 대응하는 세부 항목 |

마우스를 올리면 선택할 영역을 테두리와 이름으로 표시하고, 클릭하면 오른쪽 패널의 해당 섹션을 열어 스크롤·강조·포커스로 위치를 알려 준다. 선택한 영역의 패널에는 관련 설정만 모으고 `전체 설정 보기`를 제공한다. 말풍선처럼 이미지/글자색/여백이 함께 필요한 요소는 한 번의 클릭으로 관련 설정 묶음을 보여 준다. 매번 전체 대화상자를 열거나 여러 선택 단계를 강제할 필요는 없다.

iOS 미리보기를 눌렀다는 이유만으로 iOS 전용 재정의를 만들면 공통 제작 흐름과 충돌한다. 공유 가능한 이미지의 첫 목적지는 공통 편집으로 하고, 클릭한 플랫폼의 현재 적용 원본과 예외를 함께 표시한다. 기존 개별 이미지가 적용 중이면 `공통 원본 변경은 이 출력에 반영되지 않음`과 현재 예외 편집/공통 연결을 제공한다. 색상은 선택한 화면에 대응하는 속성으로 이동하며, 전역 팔레트를 임의로 수정하지 않는다. 선택과 탐색만으로 프로젝트 데이터·실행취소 이력·생성 입력을 변경하지 않는다.

### 구현 방향

- `renderPlatform()`에서 실제 그리는 위치와 함께 의미 있는 선택 영역을 반환한다. 대상에는 화면, 플랫폼, 역할, 상태, 관련 공통 슬롯/속성/실제 출력 경로를 담는다. 별도 좌표표로 화면을 복제하지 않는다.
- 긴 메시지의 가변 높이, 첫/연속·선택 말풍선, 프로필 변형, 지역 탭, 비밀번호 자리 수, 패턴 모드가 바뀔 때 선택 영역도 다시 생성한다. 작은 글자·아이콘은 누르기 쉬운 영역을 제공하고 겹치면 구체적인 전경 요소를 우선한다. 배경은 빈 영역에서 선택한다.
- CSS 표시 크기와 Canvas 좌표를 변환해 축소 화면에서도 정확히 선택한다. 호버/선택 테두리는 별도 오버레이에 표시해 미리보기 PNG와 실제 생성 이미지에 섞이지 않게 한다. 장식·기기 상태바·샘플 날짜 등 편집할 수 없는 부분은 편집 가능한 요소처럼 안내하지 않는다.
- 기존 catalog-editor에 화면/탭/속성/리소스/배율을 지정하는 이동 API를 추가한다. 새 편집기를 복제하지 않으며, 공통 원본 행에도 안정적인 이동 식별자를 제공한다. 비동기 상세 로딩 중 다른 대상을 선택해도 마지막 선택을 유지한다.
- 터치와 키보드에서도 같은 대상을 선택할 수 있도록 현재 화면의 `수정할 부분` 목록을 제공한다. 미리보기에 나타나지 않는 항목은 역할·한글 별칭·공식 식별자로 검색하고 해당 화면/설정으로 이동하는 탐색을 후속 보완한다. 화면에 렌더링되지 않는 가로·태블릿·배율 전용 출력은 기존 전체 목록에서 접근한다.

우선 구현 범위는 여섯 대표 화면의 주요 영역 클릭 → 기존 편집기의 정확한 항목 이동과 선택 표시다. 공통 리소스 기본 노출과 함께 적용하면 `어디서 바꾸는가`와 `두 플랫폼에 어떻게 함께 적용하는가`를 같은 동선에서 해결할 수 있다. 생성 규칙을 유지하는 선택·탐색 UI만으로는 compilerVersion 변경이 필요 없다.

구현 검증에는 양 플랫폼·축소/좁은 화면의 좌표, 겹치는 요소의 우선순위, 긴 메시지와 모든 지원 상태, 클릭 후 정확한 설정/원본/배율의 표시, 키보드 포커스, 선택만으로 프로젝트 JSON 불변, 빠른 연속 선택, PNG 캡처에 선택 테두리가 포함되지 않는지를 추가한다. 이번 추가 검토에서는 UI를 구현하거나 브라우저 검증을 실행하지 않았다.

## 말풍선 위 캐릭터 장식 (첨부 화면 추가 검토)

첨부 화면의 프로필과 별개로 말풍선 위쪽에 붙어 있는 작은 캐릭터 장식을 기준으로 검토했다. 사용자 화면의 대화 내용이나 인물 정보는 문서에 옮기지 않는다. 캡처만으로 해당 테마 원본이 어떤 이미지/속성을 사용했는지는 확정할 수 없다.

현재 Studio에는 독립적인 `말풍선 장식 이미지` 슬롯과 배치·크기 편집 UI가 없다. SLOTS와 확보한 카탈로그에는 보낸/받은 말풍선의 첫·연속·iOS 선택 이미지만 있으며, 미리보기도 해당 말풍선 이미지를 늘려 그린다. 기존 기능으로 장식을 포함한 투명 PNG를 직접 제작해 말풍선 이미지 전체를 교체하고, 내용 여백과 늘림 구간을 조정하는 경로는 사용할 수 있다. 장식 PNG만 올려 기존 말풍선과 자동 합성하는 기능은 없다.

일반 업로드 말풍선은 64×56 논리 크기로 강제 변환되며 iOS 여백 검증도 이 크기를 기준으로 한다. Android 원본 .9.png는 원본 내부 크기/가이드를 보존하는 별도 경로가 있다. 따라서 첨부와 같은 큰 상단 장식을 기존 일반 업로드로 원형 그대로 재현할 수 있다고 보장하면 안 된다. 장식이 늘어나는 영역에 걸리지 않도록 배치하고, 글자와 겹치지 않는 내용 여백이 필요하다.

개선 후보는 말풍선 설정 안에서 보낸/받은 장식 원본을 별도로 등록하고 위치·크기·글자 영역을 조절하되, 생성 시에는 지원되는 말풍선 이미지에 합성하는 방식이다. 편집기 입력을 나누는 것과 카카오톡의 별도 출력 슬롯을 추가하는 것은 구분한다. 양 플랫폼 공통 원본, 첫/연속 상태 적용 범위, 선택 상태, 장식 보존용 늘림/내용 좌표와 미리보기/실제 출력 일치를 함께 설계해야 한다. 논리 크기를 확장한다면 기하·검증·카탈로그·원본 추적·백업·캐시와 compilerVersion까지 함께 수정하고 실제 APK/ktheme를 생성해 확인한다. 실제 테마 원본 또는 공식 규격 확인 없이 별도 장식 슬롯 지원이나 첨부 화면과 동일한 실제 카카오톡 렌더링을 단정하지 않는다.

이번 확인은 소스·카탈로그 대조이며 장식 편집 기능 구현이나 새로운 생성/기기 검증은 수행하지 않았다.

## 말풍선 본체 + 장식 조합의 구체안

후속 요청의 필수 조합은 `캐릭터 + 사용자 말풍선 이미지`와 `캐릭터 + 색상으로 만든 말풍선`이다. 말풍선 본체와 장식을 독립 입력으로 두고, 장식은 선택 사항으로 설계한다.

| 본체 모드 | 장식 | 편집 결과 |
|---|---|---|
| 색상 | 없음 | 지정 색상의 기본 말풍선 |
| 색상 | 있음 | 자동 생성한 말풍선 + 캐릭터 |
| 이미지 | 없음 | 사용자 말풍선 이미지 |
| 이미지 | 있음 | 사용자 말풍선 이미지 + 캐릭터 |

`색상` 모드에서는 본체 이미지를 요구하지 않는다. 색상·모서리·꼬리·글자색·내용 여백으로 본체를 만들고 장식을 합성한다. 색상은 보낸/받은 말풍선에만 적용하며 전역 팔레트를 임의로 바꾸지 않는다. `이미지` 모드에서는 사용자가 등록한 본체의 색을 보존하고, 기존 늘림·여백 편집을 제공한다. 색상 모드로 전환해도 등록한 본체 원본은 보존해 다시 이미지 모드로 돌아갈 수 있게 한다.

### 최소 설정 UI

- `보낸 말풍선 / 받은 말풍선`: 각각 독립 설정, 공통 원본은 양 플랫폼에 적용.
- `본체: 색상 / 이미지`: 색상일 때 색상·모서리·꼬리, 이미지일 때 등록/교체와 늘림·여백.
- `캐릭터 장식: 사용 안 함 / 이미지 등록`: 투명 PNG 기준의 비율 보존 크기, 위쪽 왼쪽/오른쪽 고정, 본체와의 간격·제한된 위치 조절. 기본 위치는 받은 쪽 왼쪽/보낸 쪽 오른쪽. 이미지 자체의 불필요한 투명 여백은 자동 제거 여부를 명시하고 원본은 보존한다.
- `표시: 첫 말풍선만 / 연속에도 표시`: 기본은 첫 말풍선만. 플랫폼이 제공하는 첫/연속 리소스에 대응시키며 임의의 메시지별·발신자별 장식을 보장하지 않는다.
- 미리보기의 장식 클릭은 장식 설정, 본체 클릭은 본체 설정으로 연결한다. 공통 합성이 적용되지 않는 출력별 예외도 보여 준다.

### 출력과 기하

편집기에서는 두 요소를 독립 보존하고, 생성 단계에서는 투명 배경의 말풍선 이미지로 합성한다. 색상 모드도 최종 출력에서는 생성 PNG/9-patch를 사용할 수 있으며, 사용자가 본체 이미지를 준비해야 한다는 의미가 아니다. 확보한 iOS 샘플은 이미지와 title-edgeinsets를 사용하고, Android 공식 가이드는 첫/연속 말풍선을 9-patch로 안내한다. 이 구조에 맞추어 실제 출력으로 검증하는 접근이다.

장식은 늘어나지 않는 위쪽 모서리 영역에 두고, 늘림 구간은 본체 안에서만 잡는다. 글자 영역의 위쪽 여백에는 장식 높이와 간격을 포함하며, 새 메시지 간격과 시간 표시도 실제 합성 이미지의 내용 영역에 맞추어 검토한다. 가로 늘림선도 장식을 통과하지 않아야 하므로, 초기 지원은 좌/우 고정 장식으로 한정하는 것이 적절하다. 가운데 고정이나 자유롭게 겹치는 배치는 단일 늘림 구조로 동일하게 유지된다고 가정하지 않는다. 짧은 메시지에서도 장식을 보존할 최소 말풍선 크기가 생기며 캐릭터를 크게 하면 말풍선/메시지 간격도 커질 수 있음을 미리보기에서 보여 준다.

현재의 일반 이미지 64×56 강제 변환을 합성 결과에 그대로 적용하면 장식이 축소·왜곡된다. 본체 영역과 장식 영역을 구분하는 논리 기하를 도입하고, iOS 실제 이미지 크기와 인셋·늘림 좌표, Android 출력별 가이드, validation 및 visual-geometry의 고정 크기를 함께 일반화해야 한다. 첫/연속과 선택 상태가 공유하는 여백도 같은 좌표계로 계산한다. 선택 상태의 본체 보정과 장식 처리를 명시적으로 분리하며 기존 명시적 선택 원본을 임의로 덮어쓰지 않는다.

새 장식 원본은 SLOTS/asset 참조 계약에 연결하고 위치·크기·상태 정책은 선택 필드로 저장하는 방향을 검토한다. 새 필드가 없는 프로젝트는 기존 경로를 사용해 결과를 보존한다. 출력별 resourceOverrides와 원본 가이드가 있는 기존 프로젝트는 새 공통 합성에 자동으로 흡수하지 않으며, `현재 예외 유지 / 공통 디자인으로 연결`을 선택할 수 있게 한다. 합성 원본 추적은 본체와 장식 양쪽 기여를 표시해야 한다.

### 권장 구현 순서와 완료 기준

1. 편집기보다 먼저 색상 본체+장식, 이미지 본체+장식의 작은 생성 검증을 만든다. 양 플랫폼의 짧은/긴 메시지에서 장식 비율·고정 위치·글자 영역을 확인한다. 기존 원본 .9.png와 iOS 선택 여백도 검증 대상이다.
2. 검증된 기하를 기준으로 보낸/받은 공통 편집, 모드 전환과 원본 보존, 첫/연속 적용 범위, 클릭 탐색을 연결한다.
3. 카탈로그·검증·provenance·캐시·원본 참조/백업·복제·실행취소·화면 연결과 compilerVersion을 함께 갱신한다. 모든 기존 출력과 상태 지원을 보존한다.
4. UI 픽셀 대조와 캡처, 단위/상태·기하/화면/편집기 회귀, 실제 APK 컴파일·서명과 ktheme 생성까지 수행한다. 실제 카카오톡 적용과 첨부 구성 재현 성공은 기기 확인 결과와 별도로 기록한다.

외부 규격 참조: [카카오 iOS 9.2.5 가이드](https://t1.kakaocdn.net/kakaocorp/Service/Theme/KakaoTalk/9.2.5_UserThemeGuide_iOS.pdf), [카카오 Android 9.2.5 가이드](https://t1.kakaocdn.net/kakaocorp/Service/Theme/KakaoTalk/9.2.5_UserThemeGuide_Android.pdf). 이 문서는 보조 규격 참조이며 현재 저장소의 확보된 26.9.0 샘플을 대체하거나 현재 실제 앱 적용 검증을 의미하지 않는다. 웹 검색에 노출된 말풍선 리소스/인셋 설명과 저장소 샘플을 대조했으며 외부 PDF 전체를 확보해 검토한 것은 아니다.

이번 후속 작업은 위 조합과 구현 순서의 설계이며 기능 구현·새 테스트 실행은 포함하지 않는다.

## 확인 결과와 구현 시 검증

이번 검토에서 다음 명령의 기존 회귀 테스트 17개가 통과했다.

```sh
node --test test/geometry-provenance.test.mjs test/coverage.test.mjs test/screen-workflow.test.mjs
```

47개 공통 원본과 146개 출력의 실제 픽셀/원본 추적 일치, 양 플랫폼 비밀번호 8개 상태, 출력별 재정의, 원본 9-patch·기하 보존, 템플릿 재등록·백업·복제·화면 연결을 확인한다. 이것은 현재 생성 구조의 근거이며 제안한 새 UI의 검증 결과가 아니다.

구현 시에는 공통 등록 한 번으로 양쪽 출력/미리보기가 갱신되는지, 기존 예외가 유지되는지, 선택한 예외만 공통 연결로 돌아가는지, 실행취소·다시실행·저장·복제·ZIP 복원 후에도 연결이 유지되는지 검사한다. 화면/브라우저/상태·기하 회귀와 캡처 확인을 수행하고, 출력 변경이 있다면 실제 APK·ktheme 통합 생성도 수행한다.

이번에는 기능 코드·compilerVersion·사용자 프로젝트·서명키·빌드 결과를 변경하지 않았다. 브라우저·실제 APK 빌드·실제 카카오톡 적용 검증은 추가 실행하지 않았다.
