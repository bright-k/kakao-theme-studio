# 카카오톡 테마 도구 구현 계획

작성일: 2026-10-25. 기준 설계: `tool-design.ko.md`.
현재 상태: 조사 및 설계 문서 완료. 아래 구현·설치 검증은 아직 시작하지 않았다.

## 개발 전략

먼저 CLI에서 자체 리소스와 서명키로 실제 파일을 만든다. 그다음 같은 엔진을 UI에 연결하고, 생성된 리소스를 사용하는 미리보기를 완성한다. 편집기 완성 후에 APK 생성 가능성을 확인하는 순서로 진행하지 않는다.

단계 A의 파일 생성과 B의 실제 적용 확인은 구분한다. 실제 기기 준비가 늦어져도 데이터 모델·편집기·자동 검증 개발은 진행할 수 있다. 단, 실제 호환성 확인은 미완료로 남기고 출시 완료로 처리하지 않는다.

## 단계별 작업과 완료 기준

| 단계 | 작업 | 산출물 | 완료 기준 |
|---|---|---|---|
| A. 생성 실험 | Android 프로젝트 정리, 중립 리소스, iOS 패키징, 자체 키 생성, Android 빌드·서명·검증 | CLI 실험, 첫 ktheme/APK, 환경 기록 | 수작업 결과 편집 없이 공통 입력으로 두 파일 생성; APK 서명과 구조 검사 통과 |
| B. 실제 적용 검증 | iPhone·Android에 설치, 목록 인식·적용·말풍선·배경, Android 다음 버전 업데이트 | 실제 화면 캡처, 지원 조합 기록, 수정 목록 | 두 기기의 목표 카카오톡에서 적용 확인; 같은 키·ID의 업데이트 확인 |
| C. 공통 엔진 | 정식 스키마, 자산 변환, 버전 프로필, 진단, 프로젝트 입출력 | core/assets/adapters/CLI | JSON만으로 재생성; 입력 누락과 좌표·배율·알파 오류를 검출 |
| D. 편집기·키 관리 | 로컬 서비스, 편집 UI, 자동 저장, 실행취소, 이미지 등록, Keychain 연동·키 백업 | 로컬 편집기 | 앱 재시작/프로젝트 이동 뒤 재편집·키 재연결; 비밀값은 프로젝트 ZIP에서 제외 |
| E. 미리보기 | 두 플랫폼 4개 화면, 가변 말풍선, 상태 전환, 원본 크롭, PNG 저장 | 예상 화면 renderer | 내보내기와 동일한 변환 결과 사용; 고정 시나리오 캡처 확인; B의 실제 화면으로 주요 차이 보정 |
| F. 생성 작업·제품 마무리 | 작업 큐·취소·부분 실패·결과 보고·설치 안내, 전체 흐름 회귀 확인 | 한 번에 생성 가능한 MVP, 실행 안내 | 새 프로젝트→편집→저장→미리보기→두 파일 생성→실기기 적용의 전체 흐름 통과 |

의존 관계는 A→B, A→C→D→E→F다. B에서 드러난 플랫폼 차이를 C/E에 반영한다. F의 최종 완료에는 B가 필요하다. 먼저 한 light 변형으로 전체 흐름을 완성한 뒤 dark 변형과 일괄 출력을 더한다.

## 작업 묶음

### A. 생성 실험

1. 현재 공식 샘플의 구조를 바탕으로 자체 Android 프로젝트를 구성하고 settings·namespace·컴파일 타깃을 정리한다.
2. SDK/JDK/Gradle/Kotlin 조합을 실험하여 빌드가 통과한 조합을 기록·고정한다. 샘플의 Java source/target과 Kotlin JVM target 정합성을 확인한다.
3. 직접 만든 배경, 기본 프로필, 탭 아이콘, 말풍선으로 기본 리소스를 대체한다.
4. 단일 입력에서 두 플랫폼 리소스와 설정을 생성한다.
5. 제작자용 release 키를 생성하고 APK 정렬→서명→verify를 수행한다.
6. ktheme 압축 구조와 이미지 참조를 검사하고 결과물 체크섬을 기록한다.

이 단계의 목표는 예쁜 테마보다 설치 가능한 산출물을 만드는 것이다. 자동 생성한 결과를 사람이 풀어서 수정하는 절차가 남으면 A가 완료된 것이 아니다.

### B. 실제 적용 검증

기기별 OS·카카오톡 버전과 빌드 ID를 기록한다. 테마 목록 표시, 이름·아이콘, 친구/채팅 목록, 채팅 배경, 짧은/긴/연속 말풍선, 잠금 화면을 확인한다. 새 APK를 같은 키·패키지 ID와 더 큰 versionCode로 만들어 업데이트한다.

실제 기기에 접근할 수 없는 경우 파일 생성과 정적 검증만 완료로 표시한다. 사용자 기기 시험이 필요해지면 생성 APK/ktheme, 체크섬, 짧은 설치·확인 항목을 먼저 준비해 전달한다. 기기 검증이 완료됐다고 추정하지 않는다.

### C. 공통 엔진

정규화 색상, 자산 역할, 논리 좌표계, 플랫폼별 지원 정보, 진단 계약을 먼저 확정한다. 필수 자산은 기본 중립 자산으로 충족하고 대체 내역을 보고한다. 사용자 미지정값과 플랫폼 미지원값을 구분한다. JSON Schema와 실제 예제를 함께 관리한다.

최소 테스트: RGBA→Android ARGB, iOS 별도 alpha, 인셋 순서와 배율, 9-patch 가이드, CSS/XML 참조 일관성, 자산 누락, 고정 플랫폼 ID.

### D. 편집기·키 관리

프로젝트 목록·저장, 기본 정책 편집, 리소스 업로드, 플랫폼별 예외, 자동 저장·실행취소를 연결한다. 키 생성·기존 키 가져오기·백업·복원을 지원한다. 비밀번호를 CLI 인자와 로그에 남기지 않는다. 키가 사라지면 새 키로 조용히 대체하지 않는다.

### E. 미리보기

고정 대화 시나리오와 플랫폼별 화면 셸을 만든다. 말풍선은 실제 생성된 이미지와 늘림·여백 정보를 사용한다. 4개 화면의 주요 지원 요소를 연결하고, 미리보기에서 요소 선택→정책 이동을 제공한다. 미지원/미검증 항목을 표시한다.

성능 목표는 색상 변경 후 예상 화면 반영 200ms 내, 기본 이미지 교체 후 변환·반영 1초 내로 잡는다. 이는 초기 목표이며 기준 장비·이미지 크기를 정해 측정한 뒤 조정한다. Android 전체 빌드가 편집 동작을 막지 않도록 별도 프로세스로 실행한다.

### F. 통합과 안정화

작업별 스냅샷, 플랫폼별 상태, 진행 이벤트, 취소, 일부 성공·재시도를 연결한다. Android 작업은 초기에는 한 번에 하나만 실행하고 iOS 생성은 독립 처리한다. 재시도는 같은 입력과 예약 versionCode로 수행한다. 앱 종료 시 중단된 작업은 다음 실행에서 복구 상태를 표시한다.

최소 회귀 시나리오: 새 프로젝트 기본 출력, 색상만 변경, 전체 이미지 교체, 길고 연속된 말풍선, 키 불일치, Android 빌드 실패 중 iOS 성공, 프로젝트 내보내기·복원, 같은 테마 다음 버전 업데이트.

## MVP 완료 정의

- 사용자가 Android 소스나 CSS/XML을 직접 편집하지 않아도 된다.
- 제작자 키를 생성한 뒤 같은 키를 자동으로 재사용한다.
- 한 프로젝트에서 iOS ktheme와 설치용 서명 APK가 생성된다.
- 네 가지 화면의 두 플랫폼 예상 화면을 검토할 수 있다.
- 작업 결과와 미리보기가 동일한 입력 revision/변환 결과를 사용한다.
- 프로젝트 백업에 비밀키가 섞이지 않고 키 복원 경로가 동작한다.
- 목표 iPhone·Android에서 실제 적용과 Android 업데이트가 확인된다.
- 지원한 카카오톡·OS·화면 범위와 남은 차이가 기록돼 있다.

## 주요 위험과 대응

| 위험 | 대응 |
|---|---|
| 공식 문서와 샘플 불일치 | 실제 빌드·적용 결과를 기록하고 버전 프로필로 고정 |
| Android 빌드 환경 문제 | A 단계에서 해결하고 의존성·도구 버전 고정 |
| 말풍선 왜곡·플랫폼 차이 | 공통 기하의 표현 범위 제한, 플랫폼 전용 예외 지원 |
| 미리보기와 실제 앱 차이 | 생성 이미지 공유, 실제 캡처로 검토, 지원 범위 명시 |
| 키 분실·변경으로 업데이트 불가 | 암호화 백업·fingerprint 검사, 자동 대체 금지 |
| 신규 카카오톡 UI 변경 | 기존 프로필 유지, 새 프로필 추가 후 재검증 |
| 실기기 준비 지연 | 독립 개발은 진행하고 적용 검증만 미완료로 추적 |

## 다음 구현 착수 단위

첫 착수 범위는 A 단계다. 구체적인 결과는 **중립 테스트 테마 입력, 실제 `.ktheme`, 자체 키로 서명한 `.apk`, 서명·파일 검사 보고서, 실행 명령과 환경 기록**이다. 이후 B에서 실기기 적용 결과를 받아 데이터 계약과 미리보기를 다듬는다.

전체 일정은 A에서 빌드 환경과 플랫폼 적용 난이도를 확인한 뒤 산정한다. 초기부터 고정 일정을 약속하기보다 위 완료 기준을 기준으로 단계별 진행 상황을 관리한다.
