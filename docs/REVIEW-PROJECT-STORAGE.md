# 프로젝트별 저장 구조 검토

구현 안내: 후속 사용자 승인에 따라 0.6.0에 구현하고 실제 사용자 데이터도 원본 보존 후 이관했다. 현재 계약과 검증은 [REVIEW-0.6.0.md](REVIEW-0.6.0.md), HANDOFF.md, VERIFICATION.md를 따른다. 아래는 구현 전 검토 기록이다.

검토일: 2026-10-26. 대상: 앱/컴파일러 0.5.0. 사용자 요청에 따른 설계 검토이며 저장소 이관과 기능 구현은 아직 하지 않았다.

## 권장 방향

설정과 자산을 프로젝트 폴더 안에 함께 두고, 각 프로젝트 안에서 `assets/<sha256>.png`를 유지한다. 프로젝트 간 물리적 공유는 없애고 프로젝트 내부에서만 같은 내용의 이미지를 재사용한다. 해시 검증과 프로젝트별 보관은 함께 적용할 수 있다.

이전 검토의 공용 해시 저장소는 정상 앱 경로의 충돌 방지에는 유효했다. 이번에는 사용자가 프로젝트 단위의 파일 관리와 독립 보관을 선호하므로 프로젝트별 물리 분리를 권장한다. 같은 그림을 여러 프로젝트에 쓰거나 복제하면 저장 용량이 늘어나는 비용은 있다.

## 최종 폴더 구조 제안

```text
.data/
  projects/
    <package-id>/
      storage.json                 # 로컬 저장 배치 버전/완료 표시
      theme.json                   # 디자인·원본 참조·고정 프로젝트 ID
      assets/<sha256>.png          # 이 프로젝트 소유 원본
      previews/<revision>/         # 재생성 가능한 캐시
      builds/<build-uuid>/         # 이 프로젝트의 새 생성 결과
      backups/<timestamp>.zip      # 명시적으로 저장한 로컬 백업
  keys/                            # 기존 제작자 키 저장소 유지
  bindings/<project-uuid>.json      # 기존 ID·인증서·versionCode 연결 유지
  .staging/<operation-uuid>/        # 이관/복원 준비, 프로젝트 목록에는 미노출
  session.json
```

폴더명은 후속 사용자 요청을 반영해 고정 packageId를 그대로 사용한다. 예를 들어 `com.bright.theme.blue_morning`은 점을 포함한 단일 폴더명이며 `com/bright/theme/blue_morning`으로 나누지 않는다. 내부 project UUID는 유지한다. 이름 변경은 theme.json의 표시 이름만 바꾸므로 경로·참조가 흔들리지 않는다. 프로젝트 JSON의 `assets/...` 상대 참조와 schemaVersion 1은 유지할 수 있다. 디스크 배치 버전은 별도 storage.json으로 관리하며, ZIP 포맷 버전과 컴파일러 버전도 각각 구분한다.

keys와 bindings는 현재 위치를 유지한다. 디자인 폴더 복사·ZIP 백업에 개인키나 비밀번호를 넣지 않으며, 이관 때문에 project ID/package ID/fingerprint/versionCode를 초기화하지 않는다. 기존 전역 builds/backups는 호환 조회를 유지하며 자동 이동·삭제하지 않는다. 새 결과부터 프로젝트 폴더 아래에 저장하는 방식으로 전환할 수 있다.

## 디렉터리명은 패키지명으로 구분 (추가 검토)

사용자가 .data에서 프로젝트를 식별하기 어렵다고 요청해, 앞선 UUID 폴더안보다 packageId 폴더안을 우선하는 것으로 수정했다. 현재 서버는 같은 데이터 루트에서 packageId 중복을 거부하고, 기존 프로젝트의 packageId 변경도 거부한다. 형식 검증은 소문자/숫자/밑줄 구간을 점으로 연결하는 방식이므로 경로 구분자를 포함하지 않는다. 현재 계약에서는 안정적인 사람이 읽는 디렉터리 키로 사용할 수 있다.

- **디스크 폴더 키 = packageId, 앱의 식별 키 = 기존 project UUID.** project-store가 UUID → 등록된 packageId → 프로젝트 루트로 해석한다. API·프로젝트 선택·기존 bindings의 식별자를 패키지명으로 일괄 교체하지 않는다. 클라이언트가 보낸 변경 packageId로 먼저 저장 경로를 고르지 않으며 기존 등록 정보와 일치하는지 검사한다.
- **이름 변경:** 표시 테마명만 바꾸며 디렉터리는 유지한다. 배포한 테마를 폴더명 가독성을 위해 새 패키지명으로 바꾸지 않는다. 패키지명 자체의 변경 기능은 이번 설계에 추가하지 않는다.
- **자동 패키지명:** 현행 `studio.localtheme.t<uuid>`는 안정적이지만 길고 사람이 읽기 어렵다. 새 프로젝트에서는 의미 있는 패키지명 입력을 안내하고, 앱에 테마 이름·패키지명·폴더 열기를 함께 제공한다. 기존 자동 패키지명은 그대로 사용하며 이름을 바탕으로 몰래 재발급하지 않는다.
- **복제:** 새 UUID·새 패키지명·새 폴더를 사용한다. 현재 자동 패키지명 생성 정책은 유지하고, 복제 시 직접 패키지명을 지정하는 UI는 필요 시 별도 범위로 구현한다.
- **복원 충돌:** 같은 패키지명으로 다른 UUID가 들어와도 병합하거나 `(2)` 폴더를 자동 생성하지 않는다. 같은 프로젝트 열기 또는 새 프로젝트로 가져오기를 명확히 구분하고, 새 프로젝트라면 새 패키지명을 발급한다. 다른 데이터 루트에서 가져온 동일 패키지 프로젝트도 이 검사를 거친다.
- **폴더 정합성:** 폴더명, theme.json의 packageId/project ID, storage.json의 등록 정보가 일치해야 한다. 수동 폴더 이름 변경·다른 프로젝트의 JSON 덮어쓰기는 불일치로 안내한다. 임의 디렉터리나 이미 존재하는 다른 프로젝트를 자동으로 채택하지 않는다.
- **이관:** 기존 UUID JSON을 읽어 그 JSON의 검증된 packageId를 대상 폴더명으로 사용한다. 대상이 이미 있으면 소유 project UUID/완료 상태를 확인한다. 같은 프로젝트의 완료된 이관만 재사용하고, 다른 프로젝트/불명확한 폴더와의 충돌은 중단·보고한다. 원본과 사용자 폴더를 덮어쓰거나 삭제하지 않는다.

keys는 여러 프로젝트가 같은 제작자 키를 사용할 수 있어 전역으로 유지하고, 기존 UUID 기반 bindings도 보존한다. 프로젝트의 theme.json과 저장소 매핑으로 소유 관계를 해석한다. 폴더명이 패키지명이라는 이유로 서명 연결이나 versionCode를 초기화하지 않는다.

검증 항목에 `.`을 포함한 단일 디렉터리, 테마명 변경 후 경로 유지, 자동 패키지명/긴 유효 이름, 새 프로젝트 및 동시 생성의 패키지 충돌, 다른 UUID의 동일 패키지 ZIP, 수동 이름 변경/정합성 오류, 패키지명 대상 이관 재실행, 같은 프로젝트의 여러 백업 루트를 추가한다. 아직 디렉터리 생성·변경·이관은 실행하지 않았다.

## 프로젝트 생명주기

| 작업 | 권장 동작 |
|---|---|
| 새 프로젝트 | 자체 theme.json과 빈 assets 폴더를 만든 뒤 등록. 다른 프로젝트의 이미지를 자동 상속하지 않음 |
| 이미지 등록/교체 | 해당 프로젝트 안에서 정규화 PNG 해시를 계산·저장. 같은 프로젝트 안의 동일 내용만 재사용 |
| 프로젝트 복제 | 현재 디자인이 참조하는 자산을 새 프로젝트 폴더로 실제 복사. 새 프로젝트 ID/패키지명과 초기 버전 유지. 이전 빌드·백업·캐시는 복제하지 않음 |
| 테마 이름 변경 | 표시 이름만 변경. 패키지명 폴더와 이미지 참조는 유지 |
| 백업/복원 | 프로젝트 설정과 현재 참조 이미지에 한정. 임시 영역에서 검사 후 새 프로젝트 폴더를 등록 |
| 보관/정리 | 프로젝트별 용량·저장 위치를 보여 주고 요청된 범위만 보관/정리. 사용자 프로젝트·이미지·빌드 자동 삭제 금지 |

프로젝트 간 하드링크는 사용하지 않는다. 수동 수정의 영향까지 분리하려면 독립 파일 복사가 필요하다. 지원 파일시스템의 copy-on-write 복제는 독립 수정이 유지되는 경우 최적화로 사용할 수 있지만 일반 파일 복사 경로도 유지한다.

## 백업 ZIP 제안

```text
<package-id>--backup-<timestamp>-<backup-uuid>/
  backup.json
  theme.json
  assets/<sha256>.png
```

- 다운로드 파일명은 안전하게 정리한 테마 이름 + 패키지명 + 시각으로 제공하고, ZIP 안의 최상위 폴더는 패키지명 + 백업 시각 + 백업 UUID를 사용한다. 서로 다른 프로젝트와 같은 프로젝트의 서로 다른 백업을 같은 위치에 풀 때 루트 theme.json 충돌을 줄인다. 같은 ZIP을 반복해 같은 위치에 풀면 같은 경로를 쓰므로 백업별 별도 압축 해제를 안내한다.
- backup.json은 포맷/버전·프로젝트 ID·파일 목록/체크섬을 기록하는 방향이 적절하다. 백업 생성 시에도 실제 자산의 해시를 검사한다. 현재 exportProject는 참조 파일을 그대로 읽는 부분이므로 보강 대상이다. 체크섬은 무결성 검사이며 제작자 인증 기능으로 표현하지 않는다.
- 캐시, 빌드 결과, 과거 백업, 키, 비밀번호, bindings, session.json, .test-data는 프로젝트 백업에 포함하지 않는다. 현재 선택한 서명키 ID는 기존처럼 null로 내보내고 키는 별도 복원한다. 결과 APK/ktheme 배포 ZIP과 프로젝트 편집용 백업은 계속 별개로 제공한다.
- 기존 루트 `theme.json + assets/` ZIP도 계속 읽는다. 신규 포맷은 명시된 루트를 사용하고, 임의 깊이에서 theme.json을 검색해 추정하지 않는다. 모호한 여러 프로젝트/manifest, 정규화 후 중복 경로, 잘못된 경로·해시·형식, 크기/파일 수 초과는 거부한다.

## 복원은 최종 등록 전까지 격리

권장 순서는 ZIP 검사 → 임시 폴더 준비 → 프로젝트/이미지 무결성 검사 → 프로젝트 ID/패키지 중복 검사 → 프로젝트 폴더 등록이다. 등록 직전에 잠금 안에서 중복을 다시 검사해 동시 요청도 처리한다. 실패하면 기존 프로젝트/폴더는 변경하지 않고 이번 작업이 만든 임시 영역만 정리한다. 서버 재시작 시에는 진행 상태와 소유 표시를 확인해 완료/미완료 준비 폴더를 구분해야 한다.

현재 API는 importProject가 자산을 공용 저장소에 쓴 다음 서버가 동일 프로젝트 ID를 검사한다. 따라서 실패한 가져오기가 미사용 자산을 남길 수 있다. 프로젝트별 저장에서는 검사와 등록의 순서를 함께 고치는 것이 적절하다.

같은 프로젝트 ID가 이미 있으면 기본은 덮어쓰기를 거부하고 기존 프로젝트 열기/새 프로젝트로 가져오기를 제공한다. 새 프로젝트로 가져오기는 기존 복제 정책대로 새 프로젝트 ID와 새 패키지명을 사용한다. 기존 ID를 유지한 덮어쓰기 복원은 별도 요청/사전 백업이 필요한 후속 동작으로 분리한다.

## 기존 데이터의 안전한 이관

1. 단일 서버 시작 시 저장소 점검 단계에서 기존 `projects/<id>.json`을 인식한다. 편집·업로드·복원·빌드를 시작하기 전 이관 잠금과 진행 상태를 확보한다. 별도 CLI도 이관 중인 저장소 사용을 거부하도록 한다.
2. 해당 프로젝트의 모든 assetReferences를 수집한다. 공통 본체/캐릭터/상태 원본과 resourceOverrides를 모두 포함한다. 없는 자산/해시 불일치는 해당 프로젝트의 이관 실패로 표시하고 원본을 그대로 둔다.
3. `.staging` 안에 theme.json, storage.json과 필요한 그림을 복사하고 원본/사본 해시와 참조 완결성을 비교한다. 이동이나 삭제로 시작하지 않는다.
4. 같은 파일시스템에서 준비된 디렉터리를 새 프로젝트 위치로 rename해 활성화한다. 목록은 완료 표시가 있는 신규 폴더를 우선하며, 같은 ID의 구형 JSON은 중복 노출하지 않는다. 신규 폴더로 활성화한 뒤에는 누락 이미지를 전역 assets에서 자동 보충하지 않고 오류를 알려 격리를 유지한다.
5. 중단 후 재실행은 완료 폴더/준비 폴더/구형 JSON을 구분해 이어가거나 실패를 보고한다. 이관 기록으로 결과를 확인하고, 원본 JSON·공유 assets·기존 빌드·백업·키·bindings는 자동 삭제하지 않는다. 현재 보관 중인 샘플 원상복원 백업도 유지한다.
6. 모든 이관이 끝나도 구형 앱을 같은 .data로 다시 실행하면 이전 JSON을 편집할 수 있으므로 다운그레이드 주의와 복구 절차를 명시한다. 롤백은 원본 보존본 기준이며 신규 편집분의 역변환까지 자동 보장하지 않는다.

신규 폴더가 활성인 프로젝트는 구형 JSON을 더 이상 저장 대상으로 쓰지 않는다. 이관 실패 상태를 숨기거나 새 빈 프로젝트로 대체하지 않는다. 현재 작업은 검토이므로 실제 사용자 .data의 이관은 수행하지 않았다.

## 코드 변경 범위

| 모듈 | 필요한 변경 |
|---|---|
| 새 project-store.mjs | 프로젝트 목록/루트 해석, 준비·등록, 이관 상태/잠금, 복제·복원 저장을 한곳에서 담당 |
| server.mjs | flat JSON 목록/저장 경로 교체. 업로드·승격·미리보기·빌드·백업에 동일 프로젝트 루트를 전달. 중복 검사는 최종 등록 전에 수행 |
| core.mjs / resources.mjs | `compile(project, projectRoot)`와 자산 참조 규칙 유지. export/import를 검증·준비·최종 등록 단계로 분리. 복제는 JSON 생성뿐 아니라 참조 이미지 복사까지 수행 |
| editor-service.mjs | 생성 이미지/자산 쓰기를 프로젝트 루트에 한정. 공용 dataRoot를 캡처한 현재 서비스 구조를 프로젝트 루트 해석 방식으로 변경 |
| android.mjs | 새 빌드 저장 위치를 projectRoot/builds로 지정하되 KeyStore와 bindings는 workspaceRoot를 사용하도록 인자를 분리. 기존 빌드 목록/다운로드 호환 유지 |
| cli.mjs | theme.json 인접 assets 해석 유지. 앱 프로젝트 폴더도 같은 저장소 규칙/잠금으로 처리. 서명 정보 루트와 이미지 루트를 구분 |
| public/app.js | 원본/미리보기 조회에 projectId 전달. 썸네일 캐시 키에 projectId 포함. 프로젝트별 리소스 목록·용량·폴더 위치/백업 안내 추가 |

모든 파일 접근은 검증한 프로젝트 ID와 등록된 패키지명 매핑, 프로젝트 상대 경로로 해석한다. 클라이언트가 임의 루트를 전달하게 하지 않으며 새 폴더의 참조·실제 경로가 다른 프로젝트나 키 저장소로 벗어나지 않게 한다. 원본 이미지 조회/복사도 해당 프로젝트 범위에서 처리한다.

현재 CLI의 compile은 입력 theme.json의 디렉터리를 이미 이미지 루트로 쓰므로 자기완결 프로젝트 폴더와 잘 맞는다. 반면 buildBoth는 같은 dataRoot를 builds와 bindings에 함께 쓰므로, 이미지 루트만 바꾸거나 dataRoot를 통째로 projectRoot로 대체하면 기존 서명 연결을 잃을 수 있다. 이 인자 분리는 필수다.

출력 파일이 같더라도 저장소·descriptor 계약 변경으로 기존 미리보기를 재사용하지 않도록 캐시 namespace/버전을 분리한다. 컴파일러/미리보기 캐시 버전 변경 여부는 실제 구현 범위에 맞춰 결정하되, 기존 가변 말풍선·원본 추적 규칙 자체는 변경하지 않는다.

## 자산 관리 UI와 정리 범위

프로젝트별로 사용 이미지 수/용량, 원본 썸네일, 쓰이는 슬롯/상태/플랫폼과 로컬 위치를 표시한다. 같은 프로젝트에서 여러 슬롯이 같은 그림을 쓰면 하나의 원본과 여러 사용처로 보여 준다. 파일의 원래 이름은 표시용 메타데이터로 보존할 수 있으나 실제 경로는 해시로 유지한다.

미사용 파일은 업로드 교체, 실행취소/다시실행, 오래 열린 편집 탭에서 다시 참조할 수 있다. 현재 ProjectHistory는 브라우저 메모리에 있으므로 현재 theme.json만 보고 자산을 자동 삭제하면 안 된다. 최초 전환에서는 자동 삭제 기능을 넣지 않고, 향후 프로젝트 보관·명시적 정리의 별도 기준을 설계한다.

## 구현 순서와 완료 기준

1. project-store와 이관/프로젝트 루트 테스트를 먼저 구현한다. 기존 데이터 보존·재실행·실패 시 복구를 확인한다.
2. 업로드·복제·편집/미리보기·컴파일·다운로드를 프로젝트 루트로 전환한다. 다른 프로젝트의 같은 이름/같은 해시/다른 그림을 바꾸거나 삭제해도 대상 밖에 영향이 없는지 검사한다. 서명키 루트/기존 bindings는 그대로 유지한다.
3. 새 ZIP과 구형 ZIP 호환, 임시 검사/등록·중복/실패·동시 요청 검증을 구현한다. 백업/복원 전후 146개 생성 이미지 해시, 설정·가이드·캐릭터와 고정 ID를 비교한다.
4. 프로젝트별 목록/용량/폴더 안내를 연결한다. 단위/API·전체 브라우저 회귀, 실제 APK/ktheme 컴파일·서명·업데이트를 실행하고 README/HANDOFF/VERIFICATION을 갱신한다.

추가 회귀에는 한 프로젝트 이미지 훼손/누락의 범위, 독립 복제 후 변경, 이름 변경, 중단된 이관 재개, 같은 ID/패키지 복원 거부 시 잔여물, 조작 ZIP/중복 루트, 구형 샘플 ZIP, 서명 fingerprint와 versionCode 유지, 키/세션/캐시/다른 프로젝트 파일의 백업 제외를 포함한다. 이번에는 소스와 현재 계약을 대조했으며 신규 저장 구조의 구현/실제 이관 테스트는 실행하지 않았다.
